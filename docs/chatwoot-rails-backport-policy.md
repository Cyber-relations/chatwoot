# Chatwoot Rails 7.2.3.2 source-backport release policy

This is a narrowly scoped release-policy change for the four HIGH/CRITICAL advisories that Rails published on 2026-11-04 for gems Chatwoot v4.18.0 ships at 7.2.3.2: GHSA-8474-xrp6-wh69 (activesupport), GHSA-wm3x-v3qw-4jh3 (actionpack), GHSA-f3w6-w445-fwh9 (activestorage, CRITICAL) and GHSA-v924-7rp8-4mxh (activestorage). The fixed range is `~> 8.0.5, >= 8.0.5.2, >= 8.1.4.1`; Rails 7.2 has no fixed release (7.2.4 of 2026-09-24 is its last, and its security support has ended), so the gems are not upgraded. This is the "当面の手当て" of docs/platform-lifecycle-plan.md §2.2: the ruby_llm source backport (docs/chatwoot-ruby-llm-backport-policy.md) applied to Rails as a sibling set of files, sharing only the independent evaluator. The ruby_llm proof and its three classifications are unchanged.

The seven canonical findings remain mandatory, once each, on the exact package, installed version, fixed range and severity below. The 2026-11-04 Trivy DB reported raw CRITICAL=1, raw HIGH=6 and source-verified fixed=7 (advisory watch run 41944452500, issue #611). The newer DB used by publisher [43236553283](https://github.com/Cyber-relations/chatwoot/actions/runs/43236553283) additionally reports two CVE aliases, so that run correctly stopped at the old seven-row contract. Review on 2026-11-12 confirmed both identities against the official Rails advisories. Publisher [43378184002](https://github.com/Cyber-relations/chatwoot/actions/runs/43378184002) on 2026-11-13 reported two further Rails IDs and an unrelated msgpack finding (CVE-2026-126366, fixed by upgrading 1.8.3 to 1.8.7). All 12 raw rows were reviewed: CRITICAL=2 and HIGH=10. The two added Rails mappings were verified against the primary sources below:

Only these four additional rows (three HIGH and one CRITICAL) are accepted, each at most once and bound to the same installed gem instance and exact source proof as its canonical advisory. They cannot replace a missing GHSA. Raw counts truthfully become CRITICAL=1..2, HIGH=6..9 and source-verified fixed=7..11; unresolved CRITICAL and HIGH must both remain zero. The full raw report is retained, and each alias has its own evaluated finding and digest-bound VEX statement naming its canonical advisory and upstream fix. No new backport or package exemption is introduced. Any unknown ID, duplicate ID, missing canonical finding, wrong package/version/path/PURL/UID/fixed range/severity, scanner error, incomplete inventory or failed proof still fails and requires review.

Each advisory names its 8.0 patch, and each commit names its advisory in a `[GHSA-…]` trailer and in the gem's CHANGELOG entry. `69aff80d11` ("Restrict the formats ffmpeg and ffprobe may open") is not part of GHSA-v924-7rp8-4mxh: its trailer and CHANGELOG entry are GHSA-3f4q-8x5m-76v8, a separate LOW advisory, and the GHSA-v924 advisory lists only 8106938fb0. It is left out with the other 8.0.5.2 commits below.

The applied change is each commit's lib/ and app/ diff exactly as upstream wrote it; its tests, CHANGELOG and guide changes are left out. `scripts/harden-chatwoot-rails.rb` carries those diffs byte for byte (UPSTREAM_DIFFS, the `git format-patch` sections with their `index` lines) and `config/chatwoot-rails-backport.json` pins each one's sha256 (`upstream_diff_sha256`). There is no adaptation: every hunk occurs exactly once in the 7.2.3.2 source and applies unchanged, only at another line (210ac22d44 at the same lines, 2fc8838300 at -13, -13 and +1, ea8c40121c at 0 and -1, 8106938fb0 at +1). The catalog pins the rubygems.org archive sha256 of each gem, the original and patched sha256 of every changed file, the entrypoint, version and license hashes, and the complete inventory of every regular file of each installed gem (activesupport 285, actionpack 187, activestorage 100 before and 102 after). To reproduce the pinned patched hashes: unpack the three pinned archives and `git apply` the lib/app sections of `https://github.com/rails/rails/commit/<sha>.patch` for the four commits; the result equals the pinned bytes, and the sha256 of those sections equals `upstream_diff_sha256`.

## Fail-closed application

The hardener runs in the build-only bundle and in the shipped Alpine 3.22 gems stage (Dockerfile), and in the test image (tests/chatwoot-test.Dockerfile), right after the ruby_llm backport. It stops the build when the interpreter is not Ruby 3.4.4 x86_64-linux-musl; when any of the three gems is installed in more than one version or root (`<gem>-<digit>…` gemspecs only, so prefixed gems such as `actionpack-page_caching` are not counted), at another version or path; when the catalog or an upstream diff differs from the pinned one; when any changed file, entrypoint, version file or license differs from the official 7.2.3.2 bytes; when an added file already exists; when any file is a symlink or under one; and when the complete inventory or the vulnerable/fixed expression counts differ. A partially patched installation is neither original nor patched and stops. Every new file is computed and checked against its pinned hash before anything is written; the added directory and files get modes 0755 and 0644. A second apply on the patched gems only verifies them.

## Exposure and behavior in Chatwoot

- GHSA-8474-xrp6-wh69: reachable. ApplicationCable::Connection authenticates nobody, Action Cable's `Subscriptions#add` and the overlay's `Toybaco::Security::CableSafeLog` call `safe_constantize` on the client's `channel`, and the notifications API calls it on `primary_actor_type`. The fix compares the first segment as a literal string; for names without regular expression syntax the result is the 7.2.3.2 result (the proof compares 140,091 cases).
- GHSA-wm3x-v3qw-4jh3: Chatwoot and the overlay pass no `each_key` return value to mass assignment. With a block `each_key` now returns the Parameters, without one an Enumerator, and yields the same keys.
- GHSA-f3w6-w445-fwh9: the shipped image has no ImageMagick (docs/chatwoot-runtime-os-policy.md), Chatwoot processes images with `:vips` (`config.load_defaults 7.0`) and has no previewers. The bundled mini_magick 4.12.0 has no `MiniMagick.cli_env=`, so upstream's own guard leaves the shipped policy unapplied, makes a `:mini_magick` application fail at boot and makes the ImageMagick analyzer raise before it reads a file ("requires mini_magick 5.1 or later"). Chatwoot's `:vips` boot and analysis are unaffected. Moving to mini_magick 5.1 or `:mini_magick` changes this and needs a new review.
- GHSA-v924-7rp8-4mxh: the image has no ffmpeg, ffprobe or ImageMagick. `Blob#open` keeps the uploaded extension only when Marcel maps it to the blob's media type, so a few declared types now get a tempfile without extension (`audio/x-m4a` for .m4a, `audio/wav` for .wav, `text/x-vcard` for .vcf, a PNG uploaded as .jpg); vips reads such files by content, and the proof analyzes and transforms one.

## Installed proof, evaluation and placement

`tests/verify_chatwoot_rails_backport.rb` runs with Bundler on the exact image, network off, read-only with only a private `/tmp` (tempfiles and the Disk service). It checks the unique installed gems, every pinned hash and inventory, the loaded source location of every patched binding and the Rails version, then boots a minimal Rails application configured like Chatwoot (load_defaults 7.0, no previewers) with no database: a schema-only adapter answers Chatwoot's `active_storage_blobs` columns and refuses to connect, so blobs are built, identified, uploaded and opened as `create_and_upload!` does, without a save. Per advisory it runs the official upstream examples (inflector_test, accessors_test, image_magick_test, the analyzer test and engine_integration_test for :vips and :mini_magick, blob_test) and shows that the vulnerable 7.2.3.2 behavior fails them, then ordinary Chatwoot behavior: ordinary constants, `each_key` with and without a block, 30 common attachment types through `Blob#open`, vips analysis and variants, and `open(tmpdir:)`. Every ImageMagick command is refused and counted (none may start), and a save must fail. `tests/chatwoot_rails_backport_test.rb` rebuilds the official 7.2.3.2 source from the installed gems by reversing the hunks, checks original → patched → idempotent, and 34 refusals (each advisory unpatched alone, a mixed or partial patch, a missing or premature policy, changed, added, hidden, missing or symlinked files and roots, drift on an otherwise official installation, other versions and catalogs); a refused apply leaves every file unchanged.

The proof runs in each Dockerfile gem stage and on the final filesystem, and in the quality gate on the test image (with the fixture test) and the production image, where the booted Chatwoot app also asserts `:vips`, no previewers and the unsecurable mini_magick that the proof assumes. The publisher runs it on the exact digest and the independent evaluator (`scripts/verify-chatwoot-ruby-llm-classification.mjs evaluate <dir> <ruby_llm catalog> <Rails catalog>`) checks it against the catalog and its own pinned call sites, inventories and test counts, binds the three gems' SPDX packages and image reachability, and requires all seven canonical raw findings, allowing only the four reviewed additional alias rows above. The classification predicate (schema 2, policy `toybaco-chatwoot-source-backport-v4`) carries both proofs and both catalog hashes; the OpenVEX document (`…/chatwoot-source-backports`) has one fixed statement per validated raw ID (seven to eleven), with each Rails statement naming its gem as subcomponent and the Rails proof hash. The daily advisory watch (scripts/advisory-watch.py) does not treat these four ids as expected: it reports them as high on every Chatwoot digest, a backported one included. Suppressing them needs a digest-bound classification whose signer, publisher workflow and ref are verified, which the watch cannot do without the image bytes (planned for N+10). Until then a false positive on a backported digest is preferred over hiding an unpatched image or a rollback target.

## Alias regression coverage

The classifier tests preserve the seven-row baseline, accept all 16 subsets of the four observed aliases in reordered input, and verify exact raw counts, untouched raw evidence, canonical fix mapping and VEX coverage. Forty-eight negative alias cases reject unknown/duplicate IDs, metadata or source-proof drift, a missing canonical ID and an unrelated HIGH. The publisher-shell suite runs the actual scan/evaluate/signature-verification commands with the eleven-row fixture (CRITICAL=2, HIGH=9), checks the printed counts, and rejects missing-canonical and unrelated-HIGH cases. A regression also checks that a scan with multiple unknown IDs reports all of them, including msgpack; it cannot be absorbed into the Rails mapping. Source catalogs, installed proofs, DB freezing, scanner options and signature requirements are unchanged.
